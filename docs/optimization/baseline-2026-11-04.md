## 1. Flash

### 分区占用

| 分区 | 偏移 | 大小 | 实际占用 |
|---|---|---|---|
| bootloader | 0x1000 | 28 KB | 25.4 KB（91%），余 2.6 KB |
| nvs | 0x9000 | 24 KB | WiFi 配置、城市、番茄设置 |
| phy_init | 0xF000 | 4 KB | |
| **factory** | 0x10000 | **1024 KB** | **964.3 KB（94.2%），余 59.7 KB** |
| storage（SPIFFS） | 0x110000 | 308 KB | **0**（设备日志 `used: 0`） |
| storage1（字库） | 0x15D000 | 2048 KB | `myFont1.bin` 1,446 KB（70.6%），余 602 KB |
| 未分配 | 0x35D000 | 652 KB | |

真正紧张的只有 factory 分区。整片 Flash 并不缺，空分区、字库分区余量和未分配空间加起来约 1.5 MB。

### app 镜像构成（987,440 B）

| 归类 | Flash |
|---|---|
| WiFi/PHY 驱动与协议栈（net80211、pp、phy、wpa_supplicant 等） | 262.7 KB |
| mbedTLS（加密/TLS） | 114.4 KB |
| lwIP/网络接口 | 89.9 KB |
| 合并字符串池（日志、断言字符串） | 88.6 KB |
| C 运行库 | 82.7 KB |
| 存储（SPIFFS、NVS、VFS、分区） | 45.7 KB |
| HTTP 客户端/服务器 | 31.6 KB |
| **业务代码 main** | **48.5 KB**（代码 17 KB，只读数据 33 KB，其中 `setting.html` 7.9 KB、`favicon.ico` 6.4 KB、图片数组 22 KB） |
| 其他（FreeRTOS、系统、驱动等） | 约 72 KB |

业务代码只占 5%。大头是 WiFi、TLS、lwIP 和字符串池，能省的空间主要在配置里。业务只用明文 HTTP，但 mbedTLS 仍然会被链接进来，因为 WPA3 要用它的加密算法，所以关掉 HTTPS 只省 2 KB。

### 只改 sdkconfig 能省多少（`size_variants.sh`）

| 组 | 改动 | app 变化 | 分区剩余 | 代价 |
|---|---|---|---|---|
| assert | 断言改静默，关 `ESP_ERR_TO_NAME_LOOKUP` | −61,152 B | 12% | 断言失败不打印文件行号 |
| nano | newlib nano 格式化 | −47,824 B | 10% | 不支持 `%lld`，要改两处 `PRId64` |
| wifi | 关企业认证、OWE、SAE-PK、IPv6 | −32,352 B | 9% | 不能连 802.1X 企业网 |
| logwarn | 日志 Info → Warn | −12,592 B | 7% | 没有 I 级日志 |
| nohttps | 关 HTTP 客户端的 HTTPS | −2,064 B | 6% | 不值得 |
| **all** | 以上全部 | **−154,624 B** | **21%** | IRAM −4.5 KB，DRAM −3 KB |

见 [#1](https://github.com/sunnyswag/DesktopScreen/issues/1)。

### 字库

黑体 18 号，XBF 格式，4bpp，覆盖 U+0020–U+9FA0，单独烧在 storage1，不占 app 分区。但绘制时只判断像素值是否 ≥ 1（`paint.c:335`），灰度信息全部浪费；索引表按整个码位范围直接寻址，约 160 KB。重新导出成 1bpp 约 0.5 MB，能腾出 1 MB 做双 OTA。见 [#3](https://github.com/sunnyswag/DesktopScreen/issues/3)。

### main/src/data 值不值得关注

| 内容 | 位置 | 大小 |
|---|---|---|
| 3 张 200×200 整屏图 | Flash | 15,000 B |
| 带 const 的图标、数字 | Flash | 约 2.8 KB |
| 没加 const 的 4 个数组（`num_size48`、`weather_icon`、`back`、`time_symbol`） | DRAM .data（Flash 另存初值） | 4,152 B |
| `gImage_num_weather_code` | 未被引用，链接时已丢弃 | 0 |

源文件 123 KB 是十六进制文本，编译后只有约 22 KB（app 的 2.2%）、4 KB DRAM（静态 DRAM 的 7.5%）。**不是值得重点关注的对象**，顺手可做的两件事：4 个数组加 const，省 4 KB DRAM；`gImage_main_page` 和 `gImage_main_page_wifi` 只差 42 字节（右上角的 WiFi 图标），只保留一张能省约 4.9 KB。压缩（PackBits 可压到 13 KB，zlib 6.8 KB）和配置裁剪的 150 KB 比起来不值得做。见 [#4](https://github.com/sunnyswag/DesktopScreen/issues/4)。

## 2. RAM

### 静态

| 段 | 已用 | 总量 | 占比 |
|---|---|---|---|
| DRAM | 55,360 B（.bss 34,696，.data 20,664） | 180,736 B | 30.6% |
| IRAM | 103,658 B | 131,072 B | 79.1%（主要是 WiFi 放进 IRAM 的优化代码） |

业务代码占 DRAM 19.6 KB，其中 15 KB 是三块 5000 B 的整屏缓冲：`screen.c` 的 `partial_data` 和 `partial_data_array` 内容完全一样；`paint.c` 的 `gImage_last_page` 只写不读。见 [#4](https://github.com/sunnyswag/DesktopScreen/issues/4)。

### 运行时堆

开机时可分配的堆有 275,336 B（DRAM 6 KB + 136 KB，D/IRAM 14 KB + 111 KB），另有 25 KB 只能放代码的 IRAM。

| 时刻 | 剩余（MALLOC_CAP_8BIT，测量固件） |
|---|---|
| 进入 app_main | 242,960 B |
| WiFi APSTA、httpd 都起来后的空闲状态（阶段 4 中位数） | 140,668 B |
| **历史最低（翻页加配网页请求期间）** | **127,032 B** |
| 最大连续空闲块（最小值） | 110,592 B，没有碎片问题 |

探针自己占 8,920 B（808 B 静态 + 8,112 B 堆），扣掉以后正式固件最忙时大约剩 **136 KB**，接近堆总量的一半。RAM 总量很宽裕，WiFi 和 lwIP 起来以后大约用掉 100 KB。

常驻在堆里、可以省的大块有两个（[#25](https://github.com/sunnyswag/DesktopScreen/issues/25)）：配网服务器的 `scratch` 缓冲 8 KB（`http_server.c:56,591`，`calloc` 后从不释放，配网接口实际只需要几百字节）；WiFi 静态 RX 缓冲 10 个 × 1.6 KB = 16 KB，降到 IDF 建议的下限 6 个能省约 6.4 KB。画页面用的 5000 B 画布是每次绘制时临时 malloc、画完 free，不算常驻。

前一天人工操作的初测（简化探针，手机真实连了 AP）测到最低 130,596 B，扣掉那个探针的约 3.4 KB 后约 134 KB，和自动剧本的结果基本一致。

### 任务栈

不算探针，一共 19 个任务，分配了 56,064 B 栈，其中 27,640 B 从来没用到，留足余量后约能收回 2.5 KB（[#25](https://github.com/sunnyswag/DesktopScreen/issues/25)）。需要关注的：

| 任务 | 栈 | 最小剩余 | 说明 |
|---|---|---|---|
| **gpio_task_example** | 2048 | **172 B**（已用 92%） | 只在有触摸时出现；初测时真人触摸是 164 B。触摸路径里调了 printf 和 ESP_LOGI，见 [#5](https://github.com/sunnyswag/DesktopScreen/issues/5) |
| ipc0 | 1024 | 428 B | IDF 系统任务，默认配置 |
| beep_task | 1024 | 480 B | 用了 53%，偏紧但没有格式化输出 |
| sys_evt | 2816 | 804 B | 事件回调里有日志 |
| wifi_net_task | 4096 | 1,072 B | 用了 74% |
| ui_page_evt_task | 4096 | 1,752 B | 翻页时用了 57% |
| httpd | 4096 | 1,864 B | 处理配网页请求时用了 54% |
| esp_timer | 4096 | 3,336 B | 只用了 760 B，可以缩 |
| wifi | 6656 | 3,640 B | IDF 默认 |

没开 newlib nano 格式化时，IDF 会给 main、sys_evt、tiT、esp_timer 这些系统任务各多分 512 B 栈（`esp_task.h` 的 `TASK_EXTRA_STACK_SIZE`）。开 nano（[#1](https://github.com/sunnyswag/DesktopScreen/issues/1)）之后，运行时堆还能再多出约 2 KB。

160 MHz 双核；`CONFIG_FREERTOS_HZ=100`；`CONFIG_PM_ENABLE` 没开，所以没有 DFS 和 tickless idle。

|---|---|---|---|

| 天气、单词页全刷（`ds_screen_full_display`） | 2 | 2.48 s | |

## 4. 功耗

还没有电流数据。下面是代理指标和静态审查的结论，实测方法见 [methodology.md](methodology.md) 第 6 节。

- **休眠链路**（`app_main.c:56-126`）：只有 APSTA 已关闭、在主页、倒计时归零三个条件同时满足才会进 light sleep。开机后倒计时 600 秒，触摸后重置为 60 秒。唤醒源是 GPIO4（触摸中断脚）低电平和 60 秒定时器。停在其他页面时永远不睡。
- **WiFi**：开机以 APSTA 模式启动，联网成功后也不关 AP，590 秒后才整体关闭。开着 SoftAP 时 STA 的 modem sleep 不生效，实测空闲时 `wifi` 任务是最大的 CPU 消耗者。断线后立即重连，没有退避。
- **CPU**：固定 160 MHz，空闲时两核合计约 99% 的时间在 IDLE 里空转，加上 100 Hz 的定时器唤醒，就算开了 tickless 也睡不了多久。
- **外设**：墨水屏每次刷完都会发深睡命令，这点没问题；蜂鸣器只把输出拉低，MCPWM 定时器一直在跑；入睡前没有让触摸芯片休眠。
- **休眠后的正确性**：时间补偿不完整，番茄钟在睡眠中停走，定时唤醒后触摸中断没有恢复。见 [#12](https://github.com/sunnyswag/DesktopScreen/issues/12)。

降功耗的主线：去掉 10 ms 定时器（[#14](https://github.com/sunnyswag/DesktopScreen/issues/14)）→ 平时不开 AP、联网完就关 WiFi（[#18](https://github.com/sunnyswag/DesktopScreen/issues/18)）→ 开 PM、DFS 和 auto light sleep，休眠条件不再限定主页（[#17](https://github.com/sunnyswag/DesktopScreen/issues/17)）。

## 5. 启动与响应

时间以 esp_timer 启动为起点，约比芯片复位晚 0.5 秒。

| 事件 | 时间 |
|---|---|
| 进入 app_main | 0.05 s |
| 第一次全刷主页完成 | 2.95 s |
| STA 拿到 IP | 3.86 s |
| 天气请求完成 | 5.60 s |
| 第二次全刷主页完成 | 6.36 s |
| 系统时间有效（SNTP） | 81.87 s（另外两次是 8.06 s、7.53 s） |

三次实测里联网、首次刷屏、天气请求的时间相差都在 50 ms 以内，可以用来对比；SNTP 对时取决于服务器响应，两次约 8 秒、一次 82 秒，不适合作为对比指标。开 WiFi 前固定等了 2 秒（`app_main.c:251`），拿到 IP 后又全刷一次主页。见 [#24](https://github.com/sunnyswag/DesktopScreen/issues/24)。

## 7. 架构

**模块依赖**（只列越层的）：

| 调用方 | 被调用的上层模块 | 位置 |
|---|---|---|
| hal/timer | ui（时间页、番茄页刷新）、driver/ft6336 | `hal/timer.c:20-23,128,134,155,162` |
| system_data | ui（发页面事件）、hal/nvs | `system_data.c:10-11,97,192,213,234,249,264` |
| net/http_server | ui、hal/pwm（蜂鸣）、net/wifi | `http_server.c:495,513,554,555` |
| net/wifi_ap_sta | ui、hal/pwm | `wifi_ap_sta.c:50,51,61` |
| net/http_request_rules | ui（直接写天气页全局） | `http_request_rules.c:44` |
| ui/ui_clock、draw/paint | hal/spi（绕过 screen 层） | `ui_clock.c:33`、`paint.c:401-404` |
| ui/ui_tomatopage | hal/nvs | `ui_tomatopage.c:219,230` |
| hal/nvs | system_data 的 setter | `nvs.c:44,86` |

**全局状态**：20 多个非 static 全局变量。`g_system_data` 被定时器 ISR、GPIO 任务、httpd、HTTP 请求任务、SNTP 回调、WiFi 事件和后台任务同时读写，全项目没有一个 mutex、信号量或临界区。

**平台耦合**：页面管理内嵌 FreeRTOS 任务和队列；字库直接调 `esp_partition_*`，分区类型号写死；数据层依赖 `esp_log`。`main/CMakeLists.txt` 把 9 个 include 目录全部平铺，任何文件都能 include 任何模块的头文件。

**已弃用的驱动**：legacy timer group、legacy I2C、legacy MCPWM，每次编译和开机都会告警。

这些和 [PLAN.md](../PLAN.md) 阶段 P（抽出 core 和 pal）的目标直接相关。见 [#21](https://github.com/sunnyswag/DesktopScreen/issues/21)、[#22](https://github.com/sunnyswag/DesktopScreen/issues/22)、[#23](https://github.com/sunnyswag/DesktopScreen/issues/23)。

## 10. 其他优化方向

除了你提到的方向，这次还评估了下面几项：

- **启动与响应**：见第 5 节和 [#24](https://github.com/sunnyswag/DesktopScreen/issues/24)。
- **可维护性**：3 条项目代码编译告警、死代码（不可达的 HTTP 时间/城市请求、不可达的粉丝页、没人用的全局变量）、复制粘贴的代码块、不生效的 `main/sdkconfig.defaults` 和 GNU Make 遗留文件，见 [#22](https://github.com/sunnyswag/DesktopScreen/issues/22)、[#23](https://github.com/sunnyswag/DesktopScreen/issues/23)。
- **开发工具链**：仓库根目录的旧 `esptool.py` 会被 `python -m esptool` 优先导入，评估当天就因此把设备误复位进了下载模式，见 [#23](https://github.com/sunnyswag/DesktopScreen/issues/23)。
- **OTA**：现在只有一个 factory 分区，不能远程升级。[#2](https://github.com/sunnyswag/DesktopScreen/issues/2) 和 [#3](https://github.com/sunnyswag/DesktopScreen/issues/3) 腾出空间后就可以改成双 OTA 分区。这是新功能，不算优化，所以没有单独建 issue。
- **可测试性**：没有任何自动化测试。手势判定、天气 JSON 解析、时间进位这些纯逻辑都和 FreeRTOS、硬件绑在一起，没法在主机上测。拆出 core（[#21](https://github.com/sunnyswag/DesktopScreen/issues/21)）以后可以加主机端单元测试；本目录的脚本可以作为回归检查的一部分。

## 优化后怎么复测

1. 用 `tools/perf/` 的脚本对优化后的提交跑同样的评估，`--out perf-out/<日期>-<提交>`；设备实测按同一份剧本操作。
2. `python3 tools/perf/compare.py perf-out/baseline perf-out/<新目录>` 生成对比表。
3. 新建 `docs/optimization/<日期>.md`，按本文的章节记录结果和对比表；把 summary.md 和 metrics.json 复制到 `data/<日期>-<提交>/`。
4. 对照各 issue 的"验收"一节逐条确认，关闭已解决的 issue。
